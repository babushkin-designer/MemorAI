# Additional Claude Opus 5.5 review

2026-10-05. Read-only CLI review using Claude Code 2.1.289; returned modelUsage confirms claude-opus-5-5. No runtime modifications or capture tests. The text below is reviewer analysis, not verified API documentation.

# Независимый разбор: треск в динамиках во время записи звонка

## Итог

Основной вывод подтверждаю. Исходник `MicRecorder.handleTap` доказывает две вещи: синхронный `AVAudioFile.write` (AAC) под `UnfairLock` и паддинг паузы неограниченной длины. Причинная связь с треском **в выводе** не доказана.

Добавляю три вещи, которые меняют план:
- метрики, на которые план опирается, частично загрязнены или могут быть слепы;
- в коде есть ещё одна тяжёлая нагрузка во время звонка;
- есть ошибка таймлайна при сочетании паузы и рестарта.

## Пропущенное: факты из кода

1. **Dictation может поднять whisper-server уже после старта звонка.**
   - `DictationManager.setCallActive(true)` сначала вызывает `stopListeningAndTranscribe()`, затем `stopServer()`.
   - Транскрипция уходит на `workQueue`. Там после ffmpeg вызывается `ensureServer()`. К этому моменту `serverProcess == nil`, поэтому он запускает whisper-server заново.
   - Запуск идёт через `Process` напрямую, мимо `ProcessRunner.suspendPostProcessing`. Затем `scheduleIdleShutdown()` держит модель 15 минут.
   - Отдельно: `stopServer()` на main и `ensureServer()` на `workQueue` пишут `serverProcess` без синхронизации.
   - Условия: диктовка была активна в момент старта звонка, и `setCallActive` действительно подключён. Вызывающий код не предоставлен, это нужно проверить.
   - Ожидаемая нагрузка: всплеск (загрузка модели и одна инференция) в начале звонка, а не прерывистая нагрузка на всём его протяжении.
   - Проверка по логу: строки `whisper-server starting/ready` после `Disabled while a call records`.

2. **Метрика tap gaps загрязнена.**
   - `handleTap` при паузе выходит до обновления `_expectedNextHost`. Первый буфер после resume засчитывается как «late callback» длиной всей паузы.
   - `restartEngine` → `rollToNextSegmentLocked` тоже не сбрасывает `_expectedNextHost`; сброс есть только в ветке смены формата в `openEngine`. Простой движка тоже попадает в gaps.
   - Поэтому строка «Tap health» без поправки на паузы и рестарты не интерпретируема.
   - Даже чистые gaps не измеряют длительность callback: буферы могут прийти поздно, но с непрерывным host time.

3. **Пауза плюс рестарт дают двойной счёт.** `scheduleConfigChangeRestart` не проверяет `_isPaused`. Сценарий:
   - пауза в t0, рестарт во время паузы, resume в t2;
   - сегмент 1 заканчивается около t0;
   - первый буфер сегмента 2 сначала пишет паддинг (t2−t0), а `_currentSegmentFirstHost` получает host time буфера **после** паддинга;
   - `MicStitcher.gaps` добавляет ещё `min(t2−t0, 30)`. Сегмент 2 сдвигается.

   Тот же сдвиг возникает, если пауза случилась до первого буфера: `_firstBufferHostSeconds` указывает на аудио, которому в файле предшествует тишина. Кроме того, паузы считаются через `Date()`, а выравнивание идёт по host clock.

4. **`AudioGlitchMonitor` может быть слеп по построению.** Неизвестно, получают ли `kAudioDeviceProcessorOverload` слушатели других процессов или только клиент, чей IO-цикл опоздал. Если верно второе, наш процесс не увидит overload звонкового приложения на динамиках. До проверки по документации ноль событий на output почти не является данными.

5. **`CallDetector.checkStatus` продолжает опрос во время записи.** Каждые 2 с: `audioProcessObjects()` и 2–3 property-чтения на объект через XPC в coreaudiod, плюс `proc_pidpath`. Это не AVAudioEngine; прошлую поправку подтверждаю. Связь этого опроса с треском — гипотеза. Проверки: кратность 2 с у треска и A/B с остановленным детектором.

## Гипотезы механизма (все не доказаны)

- **H1. Общая нагрузка** → опоздание IO у звонкового приложения или coreaudiod. Источники: whisper из п.1, HEVC-кодирование всего экрана, SCStream.
- **H2. Захват системного звука SCStream** меняет путь вывода в coreaudiod. Это неизвестный контракт; проверка — A/B с выключенным SCStream audio.
- **H3. Блокировка tap.** Для треска в выводе нужна цепочка из трёх условий:
  - (а) tap выполняется на IO-потоке — неизвестно;
  - (б) наш процесс является IO-клиентом output-устройства — проверяемо через `kAudioProcessPropertyIsRunningOutput` для своего PID, тот же API, что `CallDetector.processIsRunningOutput`;
  - (в) опоздание одного клиента портит микс другим — неизвестный контракт HAL.

  Без этой цепочки блокировка tap даёт потерю **входа** в нашем файле, а не треск в динамиках. Ставлю H3 ниже H1 и H2.
- **H4. Второй input-клиент** на встроенном микрофоне взаимодействует с voice processing звонкового приложения. Snapshots показывают неизменные rate и buffer, но внутренности VPIO снаружи не видны.

## Требуют авторитетной документации

- Поток и QoS блока `installTap`; является ли он real-time.
- Время жизни `AVAudioPCMBuffer` после возврата из tap.
- Ждёт ли `removeTap` завершения callback, который уже выполняется (`stop()` на это полагается).
- Сохраняет ли AVAssetWriter PTS-разрыв в аудио (на этом построен весь паддинг).
- Открывает ли AVAudioEngine, у которого используется только `inputNode`, output IO.
- Межпроцессная семантика `kAudioDeviceProcessorOverload`.
- Учитывает ли `AVAudioFile.length` AAC priming.

## Критика bounded writer

Как улучшение надёжности записи — да. Но:

- **Lock-free не обязателен.** `os_unfair_lock`, удерживаемый только на memcpy в предвыделенное кольцо, допустим. Главное — никогда не держать его во время encode или IO. Новая зависимость (Atomics) не нужна.
- **Паддинг на writer остаётся O(pause) работы перед post-resume аудио.** Час паузы — это секунды AAC-кодирования, и кольцо переполнится по нашей же вине. Два варианта:
  - писать тишину инкрементально во время самой паузы, пока кольцо пусто;
  - хранить явные метаданные паузы без 30-секундного cap.

  Первый вариант меняет политику «stop во время паузы» (появится хвостовая тишина). Безопасно ли это, зависит от AudioMuxer, а его исходник не предоставлен. Решать после его чтения.
- **Pause/resume — маркеры в той же очереди**, что и аудио, с host time, а не `Date()`.
- **Overflow:** тишина ровно на число потерянных кадров плюс счётчик.
- **Критерий приёмки writer** — отсутствие потерь и ограниченная latency продюсера, а не «треск исчез».

## Инварианты

1. Frame 0 каждого файла-сегмента соответствует его `firstBufferHostSeconds`, с учётом предшествующего паддинга.
2. Кадры сегмента = аудио + паддинг паузы + тишина за overflow. Таймлайн никогда не сокращается.
3. Каждую паузу компенсирует ровно один механизм: файл или стичер, не оба.
4. Gap-метрика сбрасывается на pause, resume и restart.
5. Stop: продюсер остановлен → кольцо слито → файл закрыт → сегмент записан. Повторный stop ничего не делает.
6. Новый формат открывается только после финализации старого файла. Recovery даёт одно событие на поколение движка; событие устаревшего поколения игнорируется.

## Тесты без железа

Ядро writer с инъецируемым sink (протокол), синтетический PCM с host times, временные файлы:

- заблокированный sink: продюсер возвращается без ожидания, overflow учитывается точной тишиной;
- drain при stop и идемпотентность stop;
- пауза до первого буфера и пауза через рестарт: `MicStitcher.gaps` не дублирует (регрессия к п.3);
- gap-метрика не считает паузы и рестарты;
- N ошибок записи → одно recovery; событие устаревшего поколения отбрасывается;
- реальный `AVAudioFile`: для LPCM длина точная, для AAC — с допуском на priming;
- `setCallActive(true)` во время транскрипции не оставляет whisper-server (инъекция launcher).

## Минимальный путь (только после окончания звонка)

0. **Лог завершённой сессии:**
   - Tap health (с поправкой на паузы и рестарты);
   - строки `Wrote … silence`;
   - строки Dictation и whisper-server;
   - SystemAudioRecorder Capture health;
   - сверка установленного бинаря с HEAD.
1. **Пассивная инструментация без изменения поведения:**
   - max и p99 длительности `handleTap` через `mach_absolute_time`, счётчики под тем же lock;
   - имя и QoS потока tap — один раз за сессию;
   - сброс `_expectedNextHost` на pause/restart;
   - reattach `AudioGlitchMonitor` при смене default device;
   - `IsRunningOutput` для собственного PID.
2. **Малые локальные фиксы с тестами:** двойной счёт pause+restart и гонка в Dictation.
3. **A/B в одноразовом звонке.** Длинные интервалы, пользователь отмечает время каждого треска. Конфигурации: без записи / только mic / только SCStream audio / + экран / CallDetector выключен.
4. **Writer handoff — отдельным изменением** с тестами выше.

Не объявлять исправленным до A/B-проверки воспроизведения. Чистый файл или ноль overload-событий это не доказывает.
